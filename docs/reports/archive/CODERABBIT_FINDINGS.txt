Finding #11: [MAJOR] user/backend/app/api/generation.py:93 - Serialize version allocation for each profile and job pair.
**Serialize version allocation for each profile and job pair.**

The next version is read with a plain `max(version_number)` query at `user/backend/app/api/generation.py:93-97`. Nothing in that query locks the profile or job row. The record is committed only after rendering, so the window between the read and the commit is wide. Two requests for the same profile and job can read the same maximum and both assign `max + 1`.

The result depends on the `GeneratedResume` schema, which is not in the supplied context. Without a unique constraint on `(profile_id, job_id, version_number)`, duplicate version rows can be stored. Version history then has more than one record for the same version. With such a constraint, one commit fails after its document has already been rendered.

Enforce uniqueness at the database level and handle the conflicting insert. Alternatively, lock the profile and job row before reading the maximum. If the renderer derives output file names from the version number alone, concurrent requests can also write the same files.
